# Design: Orchestrated Saga for Subscribe/Unsubscribe across notifier and scanner

## Context

`notifier` and `scanner` currently share one Postgres database (`POSTGRES_URL`). `scanner` reads
the full repo list from notifier over HTTP (`GET /internal/repos`) on every scan cycle and has no
data of its own — there's no real distributed-transaction problem because there's only one
database.

This design gives `scanner` its own database and its own `tracked_repos` table, making it a true
second participant with its own local transactions. That turns "subscribe to a repo" and
"unsubscribe (last subscriber leaves)" into genuine distributed transactions spanning two services,
coordinated by an orchestrated Saga living in `notifier`.

## Goals

- `scanner` owns and scans from its own Postgres database; it no longer depends on notifier's
  `/internal/repos` for its scan loop.
- Subscribing a user to a new repo and unsubscribing the last subscriber from a repo are each
  implemented as an orchestrated Saga with explicit steps, persisted state, and compensation.
- Saga state is persisted in a new `sagas` table in notifier's database, so every saga run is
  auditable (status, steps completed, timestamps) — this is the orchestrator's saga log.

## Non-goals

- No saga for the release-notification flow (scanner → RabbitMQ → notifier email). That flow stays
  as eventual-consistency pub/sub, which is the correct pattern for it.
- No automatic background recovery/retry of crashed sagas. If notifier crashes mid-saga, the saga
  row is left in `COMPENSATING`/`STARTED` state for manual inspection — out of scope for this
  assignment.
- No saga framework/library — a small hand-rolled orchestrator is enough at this scale.

## Architecture

```
notifier (orchestrator)                         scanner (participant)
┌──────────────────────────┐   POST /internal/repos/enroll    ┌─────────────────────┐
│ SubscriptionSagaService  │ ───────────────────────────────► │ internal.router      │
│  - subscribe saga        │   DELETE /internal/repos/:id      │  enroll/unenroll      │
│  - unsubscribe saga      │ ───────────────────────────────► │  endpoints            │
│                          │ ◄─────────────────────────────── │                       │
│ sagas table (saga log)   │      200 / 4xx / 5xx              │ tracked_repos table   │
│ repos / subscriptions    │                                   │ (own Postgres DB)     │
│ (notifier's own DB)      │                                   │                       │
└──────────────────────────┘                                   └─────────────────────┘
```

- **notifier** is always the orchestrator for both sagas (it's where the user-facing request
  lands).
- Communication for saga steps is **synchronous HTTP**, reusing the existing internal-router +
  `x-api-key` pattern. The orchestrator calls scanner and waits for a direct success/failure
  response before deciding whether to compensate.
- `scanner`'s scan loop (`ScannerService.run`) switches to reading from its own `tracked_repos`
  table instead of calling notifier's `/internal/repos`. That notifier endpoint is removed.

## Data model

### notifier: new `sagas` table

```ts
export const sagaTypeEnum = pgEnum('saga_type', ['SUBSCRIBE', 'UNSUBSCRIBE']);
export const sagaStatusEnum = pgEnum('saga_status', [
  'STARTED',
  'COMPLETED',
  'COMPENSATING',
  'COMPENSATED',
  'FAILED', // compensation itself failed — needs manual fix
]);

export const sagas = pgTable('sagas', {
  id: uuid('id').primaryKey().defaultRandom(),
  type: sagaTypeEnum('type').notNull(),
  status: sagaStatusEnum('status').notNull().default('STARTED'),
  payload: jsonb('payload').notNull(), // { email, repo } or { repoId, repo }
  stepsDone: jsonb('steps_done').notNull().default('[]'), // string[] of step names completed
  error: text('error'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
});
```

### scanner: new database + `tracked_repos` table

Scanner gets its own Postgres connection (new env var `SCANNER_POSTGRES_URL`), its own
`drizzle.config.scanner.ts`, its own `migrations/scanner` output directory, and its own schema
file `src/apps/scanner/db/schema.ts`:

```ts
export const trackedRepos = pgTable('tracked_repos', {
  id: uuid('id').primaryKey(), // same UUID as notifier's repos.id — set explicitly, not generated
  repo: text('repo').notNull().unique(),
  last_seen_tag: text('last_seen_tag').notNull(),
  checkedAt: timestamp('checked_at').defaultNow().notNull(),
});
```

The `id` is supplied by notifier during enrollment (not auto-generated by scanner) so that the
`repoId` in the `new_release_detected` RabbitMQ event — which notifier's
`release-notification.consumer.ts` uses to look up subscriptions — stays valid without a mapping
table.

`docker-compose.yml` gets a second Postgres service, e.g. `scanner-postgres`, with its own volume
and port (e.g. `5433:5432`).

## Saga flows

### Subscribe saga (new repo + subscription)

Triggered from `SubscriptionService.subscribe` only on the **first** subscription to a repo (i.e.
when `repoService.findOrCreateRepo` would otherwise create a brand-new repo row). Existing-repo
subscriptions skip the saga entirely — scanner is already tracking that repo.

Steps:

1. **T1 — `createRepoAndSubscriptionLocally`**: existing logic — fetch tags from GitHub, insert
   into notifier's `repos` and `subscriptions` tables (local DB transaction).
   **C1 — `deleteRepoAndSubscriptionLocally`**: delete the rows created in T1.
2. **T2 — `enrollRepoInScanner`**: `POST {SCANNER_API_URL}/internal/repos/enroll` with
   `{ id: repo.id, repo: repo.repo, lastSeenTag: repo.last_seen_tag }`.
   **C2 — `unenrollRepoInScanner`**: `DELETE {SCANNER_API_URL}/internal/repos/:id`.

On success: confirmation email is sent **after** the saga completes (unchanged
`sendConfirmationOrFail` logic), so a failed saga never sends an email for a repo that isn't
actually being tracked.

On T2 failure: compensate by running C1 (delete the local repo/subscription), mark saga
`COMPENSATED`, and return the existing `DomainErrorCode` (treat scanner enrollment failure as a
repo-validation-style failure to the caller).

### Unsubscribe saga (last subscriber leaves)

Triggered from `SubscriptionService.confirmUnsubscribe` only when, after removing the subscription,
`subscriptionRepository.countByRepoId` returns 0 (i.e. exactly the branch that currently calls
`repoService.removeRepo`).

The subscription removal itself (`removeSubscription`) is **not** part of the saga — the user-facing
unsubscribe must succeed regardless of repo cleanup. The saga only covers cleaning up the
now-orphaned repo:

1. **T1 — `unenrollRepoInScanner`**: `DELETE {SCANNER_API_URL}/internal/repos/:id`.
   **C1 — `enrollRepoInScanner`**: `POST .../internal/repos/enroll` with the repo's last known data
   (re-create the scanner-side row).
2. **T2 — `deleteRepoLocally`**: delete the row from notifier's `repos` table.
   **C2 — `recreateRepoLocally`**: re-insert the row notifier just deleted (same id/repo/tag).

If T1 fails: nothing to compensate, saga marked `FAILED` with the error, repo stays in notifier
**and** scanner — logged for manual cleanup, user's unsubscribe still succeeded.
If T2 fails after T1 succeeded: compensate C1 (re-enroll in scanner) so scanner and notifier don't
diverge, saga marked `COMPENSATED`.

## Orchestrator implementation

A small generic runner shared by both sagas, e.g. `src/apps/notifier/saga/saga-runner.ts`:

```ts
type SagaStep<Ctx> = { name: string; run: (ctx: Ctx) => Promise<void>; undo: (ctx: Ctx) => Promise<void> };

async function runSaga<Ctx>(type: SagaType, payload: object, steps: SagaStep<Ctx>[], ctx: Ctx) {
  const saga = await sagaRepository.create(type, payload);
  const done: SagaStep<Ctx>[] = [];

  try {
    for (const step of steps) {
      await step.run(ctx);
      await sagaRepository.markStepDone(saga.id, step.name);
      done.push(step);
    }
    await sagaRepository.markCompleted(saga.id);
  } catch (err) {
    await sagaRepository.markCompensating(saga.id, err);
    try {
      for (const step of done.reverse()) await step.undo(ctx);
      await sagaRepository.markCompensated(saga.id);
    } catch (undoErr) {
      await sagaRepository.markFailed(saga.id, undoErr);
    }
    throw err;
  }
}
```

`SubscriptionService` calls `runSaga('SUBSCRIBE', { email, repo }, subscribeSteps, ctx)` /
`runSaga('UNSUBSCRIBE', ..., unsubscribeSteps, ctx)` instead of its current inline logic for those
two branches.

## New internal HTTP endpoints (scanner)

Added to a new `internalRouter` in scanner (mirrors notifier's existing one — `apiKeyMiddleware` +
`x-api-key`):

```
POST   /internal/repos/enroll      body: { id, repo, lastSeenTag }   -> 201 { data: trackedRepo }
DELETE /internal/repos/:id                                          -> 200 { message }
```

Both are idempotent: enroll upserts on `id`/`repo` conflict, unenroll is a no-op delete if the row
doesn't exist. Idempotency matters because a saga step might be retried by the caller in failure
edge cases (e.g. timeout where the call actually succeeded).

Removed from notifier: `GET /internal/repos` (no longer consumed by anyone after scanner switches
to its own table). `GET /internal/subscribers` and the tag-update endpoint stay if still used by the
release-notification flow — verified during implementation, not changed by this design.

## Error handling

- Network/timeout errors calling scanner are treated the same as explicit 4xx/5xx — any failure of
  a saga step triggers compensation of everything done so far.
- Compensation steps are best-effort with logging; if a compensation step itself throws, the saga
  is marked `FAILED` (not `COMPENSATED`) so it's visible that manual intervention is needed — this
  state should never be silently swallowed.
- All saga-related errors surface through the existing `DomainError`/`Either` pattern at the
  `SubscriptionService` boundary, so the HTTP/gRPC layers don't need to change.

## Testing

- **Unit**: `saga-runner.ts` tested in isolation — success path, T2-fails-compensates-T1 path,
  compensation-itself-fails path (mocked steps).
- **Unit**: subscribe/unsubscribe saga step functions tested individually with mocked
  repositories/HTTP client.
- **Integration** (`tests/integration`): using existing testcontainers setup, spin up notifier's DB
  + a second Postgres container for scanner's DB; exercise the full subscribe saga hitting real
  scanner HTTP endpoints (in-process scanner app or a lightweight test double), asserting rows
  exist/don't exist in both DBs after success and after a forced scanner-side failure.
- Existing subscribe/unsubscribe tests for the "repo already exists" branch (no saga involved)
  should be unaffected — explicitly verify they still pass unchanged.

## Migration/rollout notes

- New env vars: `SCANNER_POSTGRES_URL`, (re-use existing `SCANNER_API_URL`/`APP_API_KEY` for the
  enroll/unenroll calls — already defined for the existing scanner↔notifier HTTP communication).
- `drizzle-kit generate`/`migrate` need to run against both schema configs (notifier's existing one
  for the `sagas` table, scanner's new one for `tracked_repos`).
- One-time backfill: existing rows in notifier's `repos` table need to be POSTed to scanner's new
  `enroll` endpoint once, so scanner's `tracked_repos` starts populated — otherwise scanning stops
  for all currently-tracked repos until each gets a fresh subscribe. (Simple one-off script, not
  part of the saga code itself.)
